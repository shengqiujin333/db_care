## 2. 稳定责任及候选架构

| 稳定责任 | 输入/输出与边界 |
|---|---|
| 板端采集 | GXHT40 + 光敏原始值→有效温湿度、有效光照；失败不能生成零样本 |
| 板端门控 | 上一有效温度与本次样本→是否发射；按升温 >0.9℃ 且有效无光，或 >35℃；成功采集即推进 prev |
| 固定传输 | 10 B Feistel/CRC 空口→网关按 ID 缓存→BLE AES 聚合；本地发射完成不等于端到端到达 |
| 手机输入适配 | BLE 明文按 ID 解码；MQTT 按既有外部顺序归因；拒绝非法输入后才进入业务 |
| 手机业务 | 接收时间、历史窗口、展示、既有报警、本地持久化与待发箱；不能反推采样时刻、光照或门控原因 |
| 云上传 | 守护与手机号门控→固定时间键入队→HTTP→成功删除/失败保留；不是传感器样本身份认证 |

候选 A：保持上述责任分层，在传感器修正局部门控、App 修正文案并诚实表达接收/缓存语义。它与现有代码结构和固定网关约束最接近，作为后续设计的优先候选；可行范围限于已观测数据的正确处理，不能承诺完整蹬被检测覆盖。

候选 B：App 对相同数值或相同帧哈希去重。可抑制缓存复读，但会丢弃真实的相同值新上报，例如持续 35.1℃ 的周期上报；不建议把它作为默认正确修复。

候选 C：协议携带单调序号/源采样时间，或增加心跳/改变板端上报条件。可改善新鲜度或降温覆盖，但需要改变当前固定边界，本能力不选择、不实现；仅保留为未来经需求变更后的比较项。不得借当前未知自行扩大范围。

## 3. 分问题记录与接口假设

### Q1：既有编码能否承载本轮数值，是否必须改网关？

- 对象：真实 `USER/src/encrytogate.c`、网关 `feistel_al.c`、`bleencrypt.c`，App `GatewayFrameCodec.kt`，版本见清单。
- 刺激：温度 x10 为 -400、-1、0、350、351、1250；湿度 x10 为 0、1、500、999、1000、100，固定四字节 ID。负温向量用于编码有符号边界，不代表该温度可在当前现场安全施加。
- 响应：6/6 真实编码/解码保留原整数、ID 和 32 B 聚合长度；Python 参考 App 大端解码后 6/6 正确，缩放一次。原始十六进制帧见 execution，数值读回见 adapter_results。
- 已证实：该样本集合无需新增字段；433 明文 `id4|temp s16le|hum u16le|CRC16le` 与 BLE `header16|id4,hum u16be,temp s16be,pad8` 的转换可行。
- 替代部分：网关接收循环中的记录装配由小型 C 适配器复现；Android 端为 Python 参考函数，未执行真实 Kotlin；未执行 MCU 射频、BLE AES 库、Android GATT 或网络。因此不是整链兼容通过。
- 设计影响：保留布局、原字节 ID、单位；不得把内部 light_valid/reason 写入空口。真实网关身份、密钥/镜像一致性和无线到达仍未知。

### Q2：能否据 BLE 读回认定发生了一笔新的传感器上报？

- 对象：`app_um2006A.c:95,167–226` 缓存/更新路径；`MqtttService.kt:736–768,818–850,916–943`；outbox 键见 CloudUploadRepository。
- 刺激 A：收到 35.1℃/100% 后无新 RF，手机在 1000、1180 秒读两次缓存。刺激 B：传感器再次真实上报相同值，再读缓存。
- 响应：真实聚合打包函数对相同记录两次输出逐字节相同；协议中没有序号/时间。Python 构造读回时间模型得到两键 `(12345678,1000)` 与 `(12345678,1180)`；App 源码每次 BLE 读回使用主机时间并进入入库/上传路径。
- 已否定：仅凭现有字节即可无损区分 A/B；仅靠 `(dev_id,time)` 即可去除源数据复读。
- 已证实：对固定时间的 HTTP 重试去重与“真实样本恰一次”是不同保证。不同接收秒的缓存复读可能刷新 UI 最近时间、产生额外记录并重复报警。
- 未知：现场缓存保持多久、是否有其他线程清理、真实固件版本与 App 行为。当前函数内 timeoutcnt 的递减位于“收到了 RF 但解码失败”分支，不是无 RF 时的周期过期证明。不能把该分支理解为可靠 TTL。
- 设计影响：在现有范围内只能诚实标注接收观察语义，并保留不可辨识限制；不得改称精确采样/上报时间或宣称完整去重。是否允许相同值去重导致漏样须由产品决策，本次未批准。

### Q3：条件上报与 App 下降报警是否存在信息缺口？

- 对象：readme/PDR 升温门控、AlarmEvaluator 的 5/10/15 min 时间窗；FEX 已确认当前固件错误地采用下降方向。
- 构造刺激：全程有效且暗，温度 x10 在 0/180/360/540 秒依次 300→310→280→270，湿度 600→600→500→450；按规范每次有效采集更新 prev。
- 响应：规范参考门控仅在 180 秒上报，后两笔降温样本不传到 App。此为明确标记的本地逻辑模型，不是实板或 AlarmEvaluator 的执行结果。
- 已证实：即使把固件方向修正确，App 仍可能没有新的降温输入；扩大历史窗不能恢复被板端过滤的信息。没有输入时不会执行当前读数的下降判定。
- 已否定：仅调整 App 轮询/历史窗即可保证所有真实降温触发下降报警。
- 未知：实际安装处蹬被后的温度/光照轨迹、发生概率和可接受覆盖。不能据此自行把升温需求改成降温。
- 设计影响：保持板端门控和 App 既有报警两种责任分离，保留 App 报警功能，但不得承诺完整覆盖。交产品与后续架构设计明确 FB-04/安装语义及覆盖限制，保持 PACC 的真实场景门槛。

### Q4：BLE 应采用严格等长校验吗？容量是多少？

- 对象：网关 `Profile/include/gattprofile.h:50` 为 160 B；`gattprofile.c:365–378,542–560` 设置和读回固定属性；`ble_send_bf[500]`、`sensorres[150]`；App codec 接受 `size >= 16*(1+count)`。
- 刺激/响应：真实打包函数在独立安全缓冲区中打包 count=1/2/9/10，返回 32/48/160/176 B；前三者装入 160 B，10 个设备超过属性容量。本实验不运行 MCU 数组索引，也未触发越界。
- 已证实：聚合有效长度和属性承载长度不同。当前 App 接受足够长度并忽略尾部，与固定 160 B 返回存在兼容理由；PSPEC §3.1 的“帧长必须等于”不能直接作为新实现修改指令。
- 已否定：把所有大于期望长度的帧一律拒绝，就一定更符合当前网关。
- 未知：真实 GATT maxLen/MTU/长读行为；当前网关实际绑定数。9 仅是 160 B 结构的算术上限，不能宣称已支持 9 台；sensorres 容量、配置数组与 BLE 实读均须交叉核验。
- 设计影响：后续接口设计应分别描述密文对齐、承载长度、有效块数及尾部策略，用真实 160 B 读回实验裁决，不改固定网关。不得凭打包器 MAX_DEV_COUNT=255 推断产品容量，也不为本轮新增多设备容量指标。

### Q5：MQTT 归因和云幂等的前置假设是否充分？

- 对象：ReadingAttribution、MqtttService、UploadPayload、CloudUploadRepository；无已授权服务器访问入口，因此没有远程请求。
- 构造刺激/响应：`1000:30,31:60,61` 对应本地顺序 `[A,B]` 和 `[B,A]` 均满足数量一致，却给 A/B 分配不同数值。该反例仅为参考映射模型；真实 Kotlin 未运行。
- 已证实：数量校验必要但不能证明顺序一致。MQTT 不带 ID，必须由发布端与手机绑定顺序的真实证据支撑。当前 App BLE 转 MQTT 路径只保存最后一个设备，并发布逗号格式（MqtttService:748–752,1278–1294），不能将其直接认定为订阅端冒号批量格式的同一生产者。
- 未知：订阅载荷的实际发布端、顺序/时间来源与主题转发、服务端运行版本、唯一键和 2xx 业务语义。迁移文档是材料，不是运行中协议证据。
- 设计影响：BLE 按 ID 与 MQTT 按顺序为不同入口适配器；不要合并为无来源的读数，更不能把外部服务当作 CH592 新增 MQTT 能力。服务器重试继续使用原 time；SQL 唯一键、超时后重试和断网补传由后续获授权专业验证独立核验。
