## 1. 系统链路、接口与同一事件关联

### 1.1 链路

```text
GXHT40 温湿度 + 光照分压
  → CW32L010 采样/判定（每 3 min；>35.0℃ 或 升温>0.9℃且无光）
  → UM2005C 433 10 B 密文帧（uid4 | temp_le2 | hum_le2 | crc16_le2）
  → 既有 CH592 网关（仅接收绑定 ID；按 bind_device_cnt 组 16 B 块
     → AES-ECB → FFE2 160 B 属性；无数据/超时为占位）
  → 安卓 App（FFE2 读取 → MTU/长度完整性 → 解密/解码 → 按 ID 本地消费
     → 本地 SQLite → MQTT 发布 → HTTP /upload_data 待发箱）
  → 既有平台（abr.py /upload_data → MySQL sensor_data，UNIQUE(dev_id,time)）
```

### 1.2 关键接口事实（当前源码）

| 项 | 事实 | 设计含义 |
|---|---|---|
| 采样节拍 | `SENSOR_SAMPLE_TICKS=3`，RTC 1 min/拍；上电有一次采样机会 | 注入/采集窗口按 180 s 规划；连续 3 个机会约 9 min |
| 判定 | `fw_core.c:112`：`cur>350` 或 `have_prev && dark && (cur-prev)>9` | 注入 367 走真实 >35℃ 分支；不修改判据 |
| 采样/冻结/发送 | `measure.c:489 temperature_process`、`:460 measure_sample`、`:590 send_data_to_gateway` | 注入点必须在 `measure_sample()` 成功之后、`sensor_decide_report()` 之前；后续冻结/帧/CRC/Feistel/发送保持原样 |
| UART1 | `debug_trace.c`：9600 8N1；`BOOT/VDD/IOTEST/IOSIG/BUS`；`S` 15 字段；`P` 冻结行；`G` 失败诊断；每行 ≤96 B 含 CRLF | 嵌入式观察点；只观测，不改业务状态 |
| 无光默认 | `LIGHT_DARK_THRESHOLD_CODE=0` → `valid=false`、`dark=false` | 常温稳定时不触发升温分支；当前也不会自然 >35℃ |
| 网关绑定 | 0xA1：`A1 count id4×N`；网关 `bind_device_cnt` 决定 `devCount`；未匹配 ID 的 433 帧被忽略 | 必须先由 App 绑定 `uid4` 再触发传感器；否则网关丢弃该笔 |
| 网关缓存 | 收到有效帧后更新 `sensorres` 并按绑定数组帧；静默不主动清零（仅解码失败计数耗尽才清零） | 网关会持续返回最后缓存值；App 每 180 s 读取会形成“同值新接收时间”的观测，不是新物理采样 |
| App 解码 | `GatewayFrameCodec`：`devCount=frame[6]`；设备块 `id4|RH_BE|T_BE|pad`；期望 `16*(1+N)` | N=1 期望 32 B；`valueSize` 必须 ≥32 且 16 B 对齐 |
| App 完整性 | `GatewayReadGuard`：MTU ≥ `16*(1+N)+3`；长度先对齐再覆盖；不足整帧拒绝 | N=1 最小 MTU 35；不补零、不拼接、不裁余 |
| App 读取周期 | `SensorCadence.SAMPLE_PERIOD_MS=180000` | 手机读取窗口与传感器 3 min 节拍对齐；网关缓存允许跨周期取到 |
| App 本地库 | `bwtemperature_database1`：`temperature(time,device_id,temperature,humidity)` 复合主键；`pending_uploads(dev_id,time,...)` | 逐 ID 入库/入待发箱；`(time,device_id)` 幂等 |
| App 上传 | `CloudUploadRepository`：门控 `guardActive && registerphone非空`（as-built `measure_state=stopping` 表示运行中）；`POST /upload_data`；2xx 才 ack；401/403/4xx 暂停自动重试并保留 | 无测试身份则不上传；平台 2xx 不等于持久化 |
| App MQTT | `CloudConfig`：`ssl://8.140.23.253:8883`；用户名=`mac_addr`，密码=`mac_addr`+既有固定后缀（见项目资料，本设计不复制）；发布 `/<mac>/a/r0`，载荷 `<epoch>:<temps>:<humis>`；若 `mac_addr` 以 `1010` 开头，按既有 `shouldPublishBle()` 分支不发布 | 需要已确认的平台网关 MAC；broker 连接/发布是独立观察点；1010 分支记录实际产品行为，不判缺陷 |
| 平台 | `POST http://8.140.23.253:5000/upload_data`；`sensor_data(phone,dev_id,time,temperature,humidity)`；`UNIQUE(dev_id,time)` + `INSERT IGNORE`（资料声明，以实际部署为准） | 真实行回读需要获准入口；2xx 不足以证明持久化 |

### 1.3 同一事件的关联键（逐用例必须写清）

1. **设备键**：传感器 `BOOT uid` 前 4 字节（`uid4`，8 位大写 HEX）＝ 433 帧 `uid_pick(4)` ＝ 网关设备块 `id4` ＝ App `MacIdBook` 8 位 ID ＝ 平台 `dev_id`。历史 `uid=6A002C00` 只作同板历史，执行时必须用当次 `BOOT` 复核。
2. **数值键**：注入温度 `367`（36.7℃，0.1℃ 单位）是本轮唯一可区分载荷；真实湿度 `h`（0.1 %RH）由当次真实采样决定。传感器 `P` 行冻结 `t/h`、网关/App 的 `T/H`、平台行必须逐项一致。
3. **时间语义**：传感器不发 RTC 绝对时间；`S/P` 的 `k` 是 RTC 累计分钟节拍。App 的 `receiveTime` 是手机系统时间；平台 `time` 是 App 上传的 epoch 秒。**不得靠时间接近猜同一笔**；用 `uid4 + 367 + h + 采集窗口` 关联，`k`/epoch 只作辅助窗口。
4. **网关身份**：App 日志 `GwID`（6 B）来自 FFE2 头块，与 `mac_addr`（平台网关 MAC）不是同一字段；两者分别记录，不互相推断。

3. 点击连接，限时等待（建议 ≤60 s）。确认：
   - 系统 Wi-Fi 状态显示已连接且 SSID 为 `ZTE_607157`（`dumpsys wifi`/`cmd wifi status`/UI 均可，保留原始行）；
   - 该网络是当前默认网络（`dumpsys connectivity`/`ip route` 有 wlan0 默认路由），不是“无默认网络”；
   - 有限可达性检查：手机到 `8.140.23.253` 的 ICMP/TCP（8883 或 5000）有界尝试，或 App 日志出现 broker 连接/HTTP 应答。ICMP 被拦截时记录并改用 App/HTTP 证据，不伪造“已联网”。
4. 失败处置：记录实际 UI/系统错误；最多有界重试 3 次；仍失败则手机/平台段 `NOT EXECUTED`，不进入 P1 平台段，不写成通过。
5. 清理：保持用户指定的测试网络连接（用户目标要求联网）；记录 SSID/IP/默认网络；不修改其他网络配置；证据中不出现密码。

### 3.3 测试身份与 App 上传门控（手机/平台段必需）

- App `CloudUploadRepository.isGateOpen()` 要求 `measure_state` 为运行中且 `registerphone` 非空；`mac_addr`（网关平台 MAC）用于 MQTT 认证/HTTP `mac` 字段。
- 必须使用**隔离的测试身份**（测试手机号 + 网关平台 MAC + 传感器 `uid4`），不得使用 `user_table` 中真实用户数据，不得编辑 SharedPreferences/数据库或伪造短信验证来绕过注册/绑定路径。
- 获取方式：由用户提供测试手机号/验证码条件，或经 App 既有注册/登录/`setMacAddress` 路径使用已批准的测试账号。若执行轮没有可用测试身份，手机上传与平台持久化段 `NOT EXECUTED`；不得把“本地入库成功”写成“平台上报通过”。
- `mac_addr` 必须来自已确认的网关平台身份（标签/用户/已确认资料），**不得猜测**；若只能确认 BLE 地址，不得直接把 BLE 地址当作平台 MAC 断言。

### 3.4 平台只读基线、持久化回读与清理

- **只读基线**（执行段按 `existing_service_ssh_inspection`）：`systemctl status user_script`、EMQX/MySQL 容器或服务状态、监听端口（5000/8883/3306）、近期服务日志、连接状态（若获准只读命令可见）；不 `sudo`、不改文件/配置/数据、不重启、不写接口、不直连数据库。凭据只从项目资料读取，不回显。
- **持久化回读**：需要获准的只读数据入口。首选只读 SQL：
  `SELECT phone, dev_id, time, temperature, humidity FROM bwusernamebase.sensor_data WHERE dev_id='<uid4>' AND time BETWEEN <t0> AND <t1> ORDER BY time;`
  绝不允许写/删。若只有 HTTP 2xx、`inserted` 字段或服务日志，**只能证明 HTTP 受理/尝试**，不能判“持久化回读通过”；对应子项记 `NOT EXECUTED`。表结构/唯一键/列名以实际部署回读为准；与资料声明不一致时记录差异，不按假设判通过。
- **清理**：测试行删除与测试绑定移除需单独授权；测试构建恢复在嵌入式执行的烧录授权内完成并记录。无授权则保留并披露（含 `uid4+367+时间窗` 可识别信息），不冒充已清理。

## 4. 用例设计

> 通用约定：每个用例先记录三端身份与环境（版本、APK 摘要、设备/API、网关地址/GwID、平台服务状态、网络 SSID），再按“嵌入式 → 手机 → 平台”的**验证顺序**判定；物理准备顺序是“网关上电 → App 绑定/读取就绪 → 传感器刺激”。每个用例保存原始证据、时间窗、期望/实际、结论与清理；单段缺失不得用其他段通过冒充。

### 4.1 P0 身份、手机联网与接收就绪（准备用例，独立判定）

> 构建选择：P0 与 N1 使用当前量产构建或**注入关闭**的测试构建；只有 P1 使用启用注入的测试构建。不得用 P1 的注入构建取 P0/N1 的“无注入”基线。

| 嵌入式 | 重新枚举 COM43；端口先开后复位/上电；不注入 | 上电五行、`BOOT uid/rst/uart`、首条 `S` | 五行齐全有序；`uid4` 可读；`q=1`；`r=0 s=0` 无 `P`；构建/下载身份记录 | COM43 原始字节/窗口、构建/下载日志 |
| 手机 | 记录设备/序列号/API；安装/启动当前 APK（首次启动如出现隐私政策，按现有 UI 完成）；确认蓝牙开、定位开、定位权限；连接 `ZTE_607157` 并确认默认网络 | 版本/APK SHA-256、设备侧摘要、SSID、默认网络、权限 | App 摘要与候选一致；Wi-Fi 为 `ZTE_607157` 且为默认网络；无权限阻断 | `dumpsys package`、`pm path`/哈希、Wi-Fi 原始状态、UI dump/截图（脱敏） |

| 平台 | 只读基线（服务/端口/日志/连接状态，若获准只读命令可见）；记录测试 `dev_id` 的时间窗基线 | 服务状态、端口、近期日志 | 服务可达且与既有部署一致；未修改/未重启；若 DB 回读无授权，记录缺口 | 只读命令输出、脱敏日志 |

**P0 判定**：上表所有“必需”项都有原始证据且一致 → PASS；任一必需项失败/缺口 → 该段 FAIL 或 `NOT EXECUTED`；不得把“App 已安装/网关已发现”写成“接收链路已就绪”。P0 的缺口会限制 P1 的对应段，但不自动把 P1 其他未受影响段写成失败或通过。

### 4.2 N1 当前默认判据下的负向：不上报、不伪造、不上传

| 端 | 准备/动作 | 观察点 | 通过判据 | 原始证据 |
|---|---|---|---|---|
| 嵌入式 | 使用当前量产构建（或测试构建但**不启用注入**）；稳定室温、现场有光；不调温/不改光；采集 ≥3 个采样机会（约 9 min）或分窗拼接 | `S` 的 `k/p/H/V/o/D/t/h/q/r/s/y`；`P/G` 有无 | 所有周期 `q=1`；`r=0`、`s=0`；无 `P`；相邻 `k` 步长 3；`V=0 D=0` 仅记 UNKNOWN，**不得**解释为“已识别有光” | COM43 原始字节/窗口、逐行原文、解析输出 |
| 手机 | 守护运行；在同一窗口至少完成 1 个 180 s 读取周期 | `link_state`、`dev/valid/valueSize`、本地 `temperature`/`pending_uploads` 行数 | 无本轮新采样值导致的读数/入库/入队/上传；若网关返回占位 → `GATEWAY_NO_DATA` 且无行；若返回历史缓存有效值 → 记录其值与 receiveTime，标注“缓存复读”，**不得**当作本轮新上报 | logcat、UI dump、MyPrefs、DB 导出 |
| 平台 | 同一时间窗只读核查（如获准） | 新行/行数/日志 | 网关无有效缓存时无本轮新行；若存在缓存复读，如实记录，不归因于新采样 | 回读行/日志（脱敏） |
| 关联/边界 | `uid4`、窗口起止、无 `367` | 三端窗口一致 | 不以时间接近猜事件；缓存复读与真实新采样分开 | 联合证据索引 |

**顺序约束**：N1 应在 P1 之前执行。P1 的注入会让网关缓存 36.7，之后再跑 N1 会看到缓存复读，不能作为“当前默认判据不产生新事件”的干净基线。若现场已有历史缓存，记录实际状态并按上表区分；不得为清缓存而改网关固件。

**N1 判定**：嵌入式 `r=0/s=0` 无 `P` 成立，且手机/平台没有由本轮采样产生的新有效读数/新上传 → PASS；若手机出现无法由既有缓存解释的新值、或 App 合成/上传了传感器未产生的值 → FAIL。网关历史缓存的复读是既有数据语义，单独披露，不算本轮新上报。

### 4.3 P1 受控注入：同一笔 `uid4+367+h` 贯穿四段

**前置**：P0 已完成（网关绑定/读取就绪，手机 Wi-Fi/测试身份/平台基线按可得性记录）；测试构建已由固件实现提供并记录身份；N1 已完成并记录实际网关缓存状态。

| 端 | 准备/刺激 | 观察点 | 通过判据 | 原始证据 |
|---|---|---|---|---|
| 嵌入式 | 下载测试构建（Keil/CW-DAPLink，`Verify OK`）；端口先开；复位/上电；第 1 次真实采样、第 2 次注入 367、第 3 次恢复 | `BOOT uid`；`TINJ`（或等价）`real/inj`；`S` 的 `p/H/t/h/q/r/s/y`；`P` 的 `rq/s/y/t/h` | 第 1 次 `S` 真实 `t`、`r=0`；第 2 次出现 `TINJ real=<real> inj=367`，`S t=367 q=1 r=1 s=1`（或按实际重试 `s=2/y`），`P t=367 h=<h>`；第 3 次 `t≈real p=367 r=0 s=0`；`uid4` 可读；帧/格式/发送逻辑未改 | COM43 原始字节/窗口、构建/下载日志、`TINJ/S/P/BOOT` 原文 |
| 手机 | 守护运行；在注入后 ≤2 个 180 s 读取周期内取证 | `MTU negotiated`、`GwID`、`dev=1`、`valueSize`、`link_state`、`id=<uid4> H=<h>% T=36.7°C`、本地 `temperature` 行、`pending_uploads`、`CloudUpload` 日志 | MTU ≥35（期望 240）；`valueSize ≥32` 且 16 B 对齐；`devCount=1`；ID/T/H 与传感器 `P` 逐项一致；`DATA_OK`；本地行 `(uid4, receiveTime, 36.7, h)`；上传发出，待发箱按成功/失败实际记录 | logcat 原文、UI dump/截图、MyPrefs、DB 导出 |
| 手机 | 观察 MQTT 与 HTTP | broker 连接状态、`/<mac>/a/r0` 载荷、`POST /upload_data` 状态/响应 | 载荷为 `<epoch>:36.7:<h>`（按绑定顺序、N=1）且 epoch 与本地接收时间一致；HTTP 状态与响应原文记录；2xx 仅表示受理 | broker 订阅端原文、App 日志、服务器请求/响应（脱敏） |
| 平台 | 只读服务核查；如获准，按 `(dev_id,time)` 回读 | 服务状态/日志；`sensor_data` 行 `(phone, dev_id=uid4, time=epoch, 36.7, h)` | 2xx **且**存在对应行 **且**字段逐项数值一致（`36.70` 与 `36.7` 数值相等；记录实际表示）；同一 `(dev_id,time)` 重试不新增行；仅 2xx 不通过 | 回读行、服务只读日志、请求/响应 |
| 关联 | `uid4 + 367 + h`；`k`/epoch 窗口 | 四段一致 | 同一事件可追溯；不用时间接近猜；缓存复读另记 | 联合证据索引 |

**P1 判定（四段全成立才 PASS）**：

1. 嵌入式：测试构建身份明确、注入可区分、真实判定/冻结/发送路径运行、`P` 冻结 `t/h` 与 `S` 一致、`s=1`（或按实际重试记录，失败则失败/未执行）。
2. 手机：真实 BLE 读取完整、`dev=1`、ID/T/H 与 `P` 一致、`DATA_OK`、本地逐 ID 消费完成、上传发出；读取不完整时整帧拒绝，不产生读数/不上传。
3. MQTT：broker 连接与载荷匹配；若 `mac_addr` 以 `1010` 开头，App 按既有 `shouldPublishBle()` 分支不发布，记录该实际分支为 N/A，不据此判 App 缺陷；若应发布而连接/凭据不可用，记录实际原因，该子项 `NOT EXECUTED`，不得用 HTTP 成功替代。
4. 平台：HTTP 2xx + 行回读字段一致；无回读入口 → 持久化 `NOT EXECUTED`，P1 不通过。
5. 任一段缺失/不一致 → 该段 FAIL/NOT EXECUTED；**不得以其余段通过冒充整链路**。

**已知副作用**：36.7℃ > App 默认阈值 35，App 可能触发“温湿度超限”提示/通知/震动；这是 App 消费的正面证据，不作为缺陷。网关缓存会在 P1 后持续返回 36.7，App 每个 180 s 读取会形成同值新 `receiveTime` 的观测/上传（接口契约既有语义）；记录并披露，不把它当作新的物理采样，也不据此判“重复上报缺陷”。

### 4.4 异常分支（P1 内设计，不另立必需用例）

| 分支 | 刺激/条件 | 期望 | 处置 |
|---|---|---|---|
| 注入未生效 | 无 `TINJ`、`S t` 仍为真实值、`r=0` | 不产生上报 | 测试构建未生效 → P1 嵌入式段 FAIL/未执行，交固件实现修构建/接口；不得改判据 |
| 433 发送失败 | `r=1` 但 `s=2`/无 `P`/重试用尽 | 按 `S/P` 实际记录重试与失败 | 记录发送失败，交实现/联调；不跳过；不得把 `r=1` 写成网关已收到 |
| 读取不完整 | `mtu<35` 或 `valueSize<32`/非 16 B 对齐 | `READ_INCOMPLETE`/`READ_INVALID`；不产生读数/不入库/不上传 | 整帧拒绝；记录 MTU/实际/期望；交 App/网关调查；不补零/不拼接 |
| App 上传被拒 | 401/403/其他 4xx | 保留待发、停止自动重试、状态可见、手动重试可用 | 记录状态/响应；保留数据；交 App/平台；不以重试冒充成功 |
| 平台无行 | HTTP 2xx 但回读无行/字段不符 | 持久化未成立 | 记录 2xx 与回读差异；交平台；2xx 不得改判通过 |
| 网关未绑定先收到 | 传感器先发送、App 后绑定 | 网关忽略该笔；App 读不到 | 物理准备顺序必须“网关→App 绑定/读取就绪→刺激”；失败则重做 P0/P1 窗口 |

### 4.5 修复与复测规则

- 任一必需项 FAIL：按责任交对应实现（固件/安卓/网关/平台）；保留原始证据与最小复现，不改判据、不删失败证据。
- 修复后必须用**当前组合版本**重新采集和判定受影响用例：新固件摘要/新 APK SHA-256/新服务状态，新一轮窗口与新关联键；旧 PASS 不沿用。
- 仅测试工具/夹具问题可在 test 范围内有界修复并记录；不得改产品源码、权限文件或环境配置来“修好”测试。
- 可选重复：时间与授权允许时，在同一测试构建上再复位/注入一次，验证 `uid` 稳定、每次上电最多一次注入、平台按 `(dev_id,time)` 幂等；不因未做重复而改判 P1 通过，但重复是独立扩展项，需单独记录。

## 6. 证据规范与保存

执行阶段建立独立目录（建议 `evidence/e2e_joint_<YYYYMMDD>/`；本设计不预建）：

1. **身份**：HEAD、`git status`、构建命令、传感器测试/发布构建摘要、网关地址/`GwID`、APK 大小/SHA-256/MD5、设备 serial/型号/API、设备侧 `base.apk` 摘要、平台服务身份/版本。
2. **环境**：手机蓝牙/定位/权限、Wi-Fi SSID/默认网络/IP、网关供电/发现状态、平台服务/端口/连接数、时间窗。

## 8. 退出准则（执行能力必须逐项回引）

1. **身份闭合**：当次传感器测试/发布构建摘要、下载 `Verify OK`、`BOOT uid`、COM43 身份；网关地址/`GwID`；App commit/APK SHA-256/设备摘要/版本；平台服务身份/基线。不得用历史 COM42/旧镜像/旧 uid/旧 APK。
2. **P0**：三端身份与接收就绪、手机 `ZTE_607157` 已连接且为默认网络、`uid4` 已绑定、0xA1 写入（N=1 为 6 B）、读取可判定；测试身份/平台回读授权按可得性记录。任一必需项失败 → P0 FAIL/相应段 `NOT EXECUTED`。
3. **N1**：嵌入式 ≥3 个机会 `r=0/s=0` 无 `P`；手机/平台无本轮新采样值导致的新读数/新上传；历史缓存复读如实区分。任一不可解释的新值/伪造 → FAIL。
4. **P1**：四段（嵌入式注入/冻结/发送；App 完整读取/解码/本地消费/上传；MQTT 按产品分支；平台受理+行回读）全部成立才 PASS；MQTT 的 `1010` 分支记 N/A，不据此判缺陷；其余任一段缺失/失败 → 该段 FAIL/`NOT EXECUTED`，不得部分通过。
5. **测试构建排除与恢复**：发布构建无 `TINJ`/测试符号/字符串；默认 0 行为一致；P1 后恢复标准构建并 `Verify OK`。未排除/未恢复 → 测试构建无效，P1 不得判通过。
6. **清理与披露**：测试绑定/本地数据/平台测试行按授权清理或保留并披露；密码/凭据未泄露；未执行项逐项列出。
7. **修复复测**：任何 FAIL 交对应实现；修复后用当前组合版本重新采集/判定；不得改判据或删证据。
8. **不伪造**：不得用串口日志代替 App 收到、用 App 2xx 代替平台行、用注入冒充物理测量、用缓存复读冒充新采样、用主机结果代替真实链路。
9. **阶段边界**：本轮通过只表示“当前组合版本下 P0/N1/P1 在指定条件成立”，不表示真实物理触发、功耗、射频电气、9 台、API 31+、正式发布或完整产品通过。
