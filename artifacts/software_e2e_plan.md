# 软件端到端测试计划（E2E-SW-002）

状态：软件测试设计产物（software_tester.software_test_design，输出端口 `e2e_plan`）
版本：1.0
范围：只保留**必须端到端证明**的关键跨系统旅程：App ↔ MQTT broker（TLS）↔ 云端 `/upload_data`，以及 App 与真实网关 BLE 读取、告警/展示的端到端一致性。
本文只做计划（旅程、前置、步骤、证据、判定、阻塞条件），**不执行**。与 `artifacts/software_test_design.md`（TD-SW-002）配套：TD-SW-002 负责分层与逐项设计，本文负责跨系统旅程。

上游输入：`readme.txt`、`artifacts/android_architecture.md`（AA-002）、`artifacts/interface_contract.md`（IC-002）、`服务器迁移记录.md`、`artifacts/test_design.md`（TD-002，嵌入式侧联测边界）。

执行原则：
- 每条旅程必须给出**两类以上独立证据**（App 侧状态/截图 + 日志 / 本地库 / HTTP 响应 / 网关或 broker 侧记录），并注明同一操作的时间对应关系；
- 刺激优先使用可脚本化软件手段（MQTT 载荷注入、HTTP 探测、adb 截图/logcat、debug 包数据库导出）；
- 不具备前置（无设备/未授权/网络不可达/无真实网关/无测试账号）时，该旅程返回 BLOCKED 并说明条件，**不得记为通过**。

## 1. 环境与诊断证据基线

| 项 | 要求/获取方式 |
|---|---|
| Android 设备 | runtime 配置的安卓目标；`adb` 授权；debug 包（`./gradlew :app:assembleDebug` 产物）；系统时间正确并记录 |
| 测试账号/绑定 | 测试手机号（`MyPrefs.registerphone`）、测试网关 MAC（`MyPrefs.mac_addr`）、至少 1 个绑定设备 ID（`MacIdBook`，`macid_name_map`）；非生产用户数据 |
| broker | `ssl://8.140.23.253:8883`（EMQX 5.8.0）；凭据规则 用户名=MAC、密码=MAC+`&^!A:z?`；TLS 信任锚 `assets/jd-ca.crt` |
| 云端上传 | `POST http://8.140.23.253:5000/upload_data`；服务端 `UNIQUE(dev_id,time)` + `INSERT IGNORE`；响应含 `inserted` 计数 |
| MQTT 刺激发布者 | 独立 clientId 的 MQTT 客户端，向 `/<mac>/a/r0` 发布构造 payload；**禁止**冒用真实网关 clientId |
| 诊断证据 | logcat（`MqttService`/`TempDb`/`DataProcessor` 及归因/上传相关 tag）、adb 截图、debug 包数据库导出（`run-as`）后宿主机只读解析、HTTP 响应原文 |
| 不可得项 | MySQL 行级直查（服务器责任方）；无真实网关时的 BLE 联调 |

## 2. 关键旅程

### J-1 云端主链路（MQTT → 归因 → 入库 → 上传 → 幂等）

**目标**：证明"一条网关遥测经 App 正确归因、以真实采样时间落库、并上传到新服务器且端到端幂等"。
**前置**：设备联网、测试账号已注册、`mac_addr` 与 1 个绑定设备 ID 就绪、守护开启（`measure_state=1`）、broker 与 `/upload_data` 可达。
**步骤**
1. 记录基线：待发箱行数、本地 `temperature` 该 devId 行数、服务端该 `(devId,time)` 已知状态。
2. 发布受控载荷 `T:24.5:55.0`（`T` = 一个未被使用过的 Unix 秒）。
3. 观察：App 卡片显示 24.5℃/55%；本地库出现 `time == T` 的行；待发箱短暂入队后清空。
4. 同一载荷**重复发布一次**。
5. 用相同载荷直接 `POST /upload_data` 再发一次（绕过 App，验证服务端唯一键）。

**证据**：logcat 原文；卡片截图；本地库导出后该 devId 的行（含 `time`）；待发箱前后行数；两次 HTTP 响应体 `inserted` 值。
**判定**：App 侧读数/入库时间与 payload 首段一致（无 `T-60` 回填）；上传请求体字段名/单位正确；重复上传与重复 POST 均不产生第二行（`inserted=0`/行数不变）；App 不崩溃。
**阻塞条件**：broker 或 `/upload_data` 不可达；无测试账号。

### J-2 BLE 真实网关链路（网关 → BLE 记录 → App）

**目标**：证明真实网关聚合帧在 App 侧被正确解码、归因并进入同一条本地/上传链路（GXHT40 换型后线上格式未变）。
**前置**：真实传感器+网关在线并已绑定到测试账号（与嵌入式能力协作）；BLE 读取在 App 中可触发。
**步骤**
1. 触发一次真实上报（传感器条件成立，由嵌入式能力配合）。
2. App 读取 FFE0/FFE2 并解码；记录 App 解析出的 `devId/temperature/humidity`。
3. 与网关侧记录（或嵌入式测试的空中帧/网关日志）逐字段对照。
4. 观察本地入库时间 ≈ BLE 接收时刻（系统时间），并触发上传。

**证据**：网关/嵌入式侧帧记录；App logcat 解析行；卡片截图；本地库行；上传响应。
**判定**：App 解析值与上游一致（含负温符号、无温湿度互换）；devId 与网关记录前 4 B 一致；入库时间为接收时刻；上传链路与 J-1 一致。
**阻塞条件**：无真实网关/无可用传感器上报 → BLOCKED（不得用 App 单测替代本旅程结论）。

### J-3 断网累积 → 恢复补传（不丢、不重）

**目标**：证明断网期间读数进入待发箱不丢失，网络恢复后补传且不产生重复数据。
**前置**：同 J-1；可切换设备网络（飞行模式）。
**步骤**
1. 开启飞行模式，确认 App 不崩溃且前台服务/BLE 轮询循环仍存活（logcat 时序）。
2. 在断网期间注入多条不同 `(devId,time)` 的读数（覆盖正常、超限、紧急各一）。
3. 记录待发箱行数与 `attempts`/`next_attempt_at` 变化。
4. 恢复网络，观察待发箱清空与请求时序（退避间隔）。
5. 对其中一条 `(devId,time)` 手工重复 POST，验证服务端幂等。

**证据**：待发箱导出（断网中/恢复后）；logcat 上传时序；HTTP 响应；服务端 `inserted` 计数；卡片/告警界面状态。
**判定**：断网读数全部保留；恢复后全部补传且每 `(devId,time)` 仅一行；退避有界不超上限；对用户无阻塞、无崩溃。
**阻塞条件**：无可控网络或待发箱不可观测。

### J-4 告警与展示全链（时间窗判定 → 事件/通知 → 早报一致）

**目标**：证明条件上报稀疏数据下，告警按**时间窗**而非"第 N 个样本"判定，且展示与报告语义一致。
**前置**：同 J-1；守护开启；每设备报警参数按已知值设置（`tempdrop`/`humdrop`/`tempmax` 等，记录实际值）。
**步骤**
1. 注入 `T-30min` 温度 30.0/湿度 60.0，再注入 `T` 温度 27.0/湿度 55.0（差 3.0℃/5.0%RH），两者之间无更近样本。
2. 观察卡片/通知与 `alarm_events`（类型 `drop`、按 devId）。
3. 负对照：注入 3 条时间都在最近 1 分钟内的样本，温度逐次下降 → 不应触发下降报警。
4. 注入 `66.0℃` → 紧急通知（不受 900 s 去抖）；900 s 内再触发一次下降/超限 → 仅一次通知。
5. 注入一条 `time = now-40min` 的读数 → 卡片**不显示"离线"**，显示相对时间与条件上报提示。
6. 生成当日早报：一台设备有数据、另一台 0 样本。

**证据**：注入 payload 与时刻；卡片/通知截图；`alarm_events` 行；早报文本；logcat。
**判定**：时间窗下降触发且负对照不触发；紧急每次通知、下降/超限 900 s 去抖；"离线"不再出现；无上报设备显示"昨日无上报"；同批数据统计值与改动前一致。
**阻塞条件**：参数不可控/通知不可观测。

### J-5 服务器迁移与 TLS 信任链

**目标**：证明 App 仅按设计切换服务器地址，TLS/认证/明文放行边界正确且未放宽安全面。
**前置**：设备联网；`network_security_config.xml` 与常量已按设计修改；`assets/jd-ca.crt` 未变。
**步骤**
1. 启动 App，观察连接 `ssl://8.140.23.253:8883` 的过程与结果状态。
2. 核对用户名/密码拼接、topic、MTU 等连接参数与基线一致（静态 diff + logcat 中的连接参数/主题）。
3. 核对明文放行域集合仅在设计允许范围内（不得新增其它主机）。
4. 负向检查：静态确认仅使用 `jd-ca.crt` 作为信任锚、无 `trust-all`/绕过校验；若可在不改动被测代码的前提下构造本地 TLS stub，则验证"证书链不属于 `jd-ca.crt` 时必须握手失败"。
5. 通过 App 走一次注册/设置 MAC 相关调用（使用无效数据，避免真实短信/写库），确认 HTTP 基址已切到新服务器且既有端点行为不变。

**证据**：logcat 连接日志与状态；静态 diff（常量/证书摘要/放行域）；HTTP 探测响应；界面状态截图。
**判定**：仅新服务器地址生效；旧 IP 无残留；TLS 基于 `jd-ca.crt` 且未放宽校验；明文放行未扩张；既有端点在语义不变的前提下可用。
**阻塞条件**：网络不可达；无法构造证书负向条件 → 该负向项记录证据强度受限，不判通过。

### J-6 条件上报语义的端到端一致性（跨能力）

**目标**：证明"3 分钟采样 + 条件上报"下，App 不合成缺失样本、不把未收到当 0、不重算传感器门控，且展示/报告与规则一致。
**前置**：真实传感器+网关（或与嵌入式能力联测环境）；App 守护开启。
**步骤**
1. 在"无变化不满足上报条件"的至少 3 个采样周期内，确认无新遥测（网关/App 均无新数据）。
2. 确认 App 未产生任何合成样本：本地库无新增行、卡片不刷新为 0 值、图表不出现虚构点。
3. 构造条件成立的一次上报（与嵌入式能力配合，例如下降 >0.9℃ 且无光，或 >35.0℃），确认 App 收到并按 J-2 全链处理。
4. 核对 App 呈现的规则文案与 readme 一致（3 分钟、0.9℃+无光、35℃），且不出现光照/lux 或 App 推断的上报原因。

**证据**：时间线（采样周期与上报时刻）、App 侧本地库/卡片/详情截图、网关或嵌入式侧上报记录、规则文案截图。
**判定**：无上报周期内 App 侧零新增（无合成）；条件成立时数据完整贯通；展示与规则一致且无光照信息。
**阻塞条件**：无真实链路/无嵌入式配合 → BLOCKED；**不得用注入数据替代"传感器真的按条件上报"的结论**（注入仅用于 App 侧行为验证）。

## 3. 证据汇总与判定规则

- 每条旅程输出一张证据索引：旅程号、执行时间、环境（设备/网络/账号/网关状态）、步骤、原始证据路径、期望、实测、结论、阻塞说明。
- 全部旅程的结论必须能被保存的原始证据复现；不得以"命令成功/退出码 0"替代业务结论。
- 前置不足或环境不可达：记录 BLOCKED 与缺失条件，不计入通过；不伪造、不外推。
- 跨能力边界：J-2/J-6 的传感器/网关侧条件由嵌入式能力提供；本计划只消费其证据，不代替其实施或判定。
