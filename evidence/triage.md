## 1. 结论摘要

1. **E1 修复在更长运行时间上仍然成立**：本轮在同一启动会话（`k=57 → 75 → 84 → 87`，无回退）中新增 3 条实板 `S` 行（全部 `q=1`、0 条 `G`）和 1 个新的位级 I²C 事务。该事务 `0x44` 写 `0xFD` + 读 6 字节 `60 30 11 6B 65 80`，双字 CRC-8 独立复算**均匹配**（20.8 ℃ / 42.0 %RH）；命令 STOP→读 START **32.516 ms**，SCL 位周期 **614.25 µs**（≈1.628 kHz，D2 慢时钟保留）。
2. **当前 `TEST_FAIL` 的剩余原因不是已证实的功能缺陷**，而是三类缺口：
   - **测试编排缺口（非固件）**：T4-02 上电五行/横幅。源码顺序为 `BOOT → VDD → IOTEST → IOSIG → BUS`，串口会话在 `Application running` 后约 68 ms 才建立，只来得及看到 `BUS`；本运行时串口采集与下载严格串行，本轮无法并发取得前四行。
   - **物理条件缺口（用户/现场）**：T5 全暗标定与三态、INT-03..07/09 遮光+升温与网关/手机同窗观测。全部新周期仍为 `V=0 D=0 o=8 r=0 s=0 y=0`，未标定门禁按设计工作。
   - **一项已确认的软件侧观测缺陷 + 一项基线偏差**（见下）。
3. **新确认的软件侧缺陷 F-1（S 行前值语义）**：`measure.c::temperature_process()` 在 `s_prev_temp_x10 = tempvalue; s_have_prev = true;` **之后**才让 `sensor_trace_fetch()` 读取前值（`measure.c:509-510` → `measure.c:543-544`），且 `main.c:264-272` 是在 `temperature_process()` 之后才发布轨迹。结果 `S` 行的 `p`/`H` 是**本周期更新后**的值：本轮 3 条新行全部 `p == t`、`H=1`；EV-026 的上电首行 `k=0 p=241 t=241 H=1` 同因。业务判定本身使用更新前前值（宿主 harness 79/79 已证），**不影响上报逻辑**；但 TD-002 INT-01 明确要求“上电后立即有首条采样（`H=0`）”，该观测要求**无法由 S 行复核**。责任：固件实现。
4. **已确认的基线偏差 F-3（`delay_ms` 实际偏长）**：配置 `GXHT40_MEASURE_WAIT_MS=20`，位级实测命令 STOP→读 START **32.516 ms**（EV-026 为 32.525 ms，比率 **1.626×**，两次独立一致）。所有 `delay_ms()` 调用点都是**下限等待**（tMEAS 20 ms、tPU 2 ms、光敏稳定 100 ms、重读 1 ms、总线诊断 1 ms），偏长方向安全，未观察到功能失败；但它与“毫秒”名义值不符，属需实现侧决策/重新标定的基线偏差。`delay_us()` 已含 `volatile`，UM2005C 的 10/50 µs 调用未受影响于 E1 改动（本轮未直接测量，见 §10）。
5. **节拍观测 F-2 重估**：由本轮窗口边界可约束稳态采样周期 **127.25 s ≤ P ≤ 184.90 s**，与 EV-026 的 ≈170 s 稳态一致；EV-026 记录的首间隔 148.0 s **落在该实测区间内**，不再作为“明显短于稳态”的异常证据；INT-01 的“≈180 s、误差不超过窗口宽度量级”判据未被违反。其 RTC 复位相位机制仍未证实，当前不影响验收。
6. 结论类型：`FAILURE_ANALYZED`（有效归因产物完成；不等于产品修复或测试通过）。

## 3. 软件侧缺陷 F-1：`S` 行 `p/H` 为“更新后前值”

| 检查 | 事实 |
|---|---|
| 判定路径 | `measure.c:499-500` 使用**更新前**的 `s_prev_temp_x10/s_have_prev` 调用 `sensor_decide_report()`；`measure.c:509-510` 之后才推进前值 |
| 轨迹路径 | `measure.c:543-544` 在 `sensor_trace_fetch()` 中读取的已是推进后的 `s_prev_temp_x10/s_have_prev`；`main.c:264-272` 在 `temperature_process()`/`send_data_to_gateway()` 之后才调用 `sensor_trace_fetch()` 并打印 |
| 打印 | `debug_trace.c:393-394` 将 `prev_temp_x10`/`have_prev` 直接打印为 `p=`/`H=` |
| 实板证据 | 本轮 3 条新行 `p==t`、`H=1`；EV-026 `k=0 p=241 t=241 H=1`（首样本本应为 `H=0`） |
| 业务影响 | **不影响**上报判定（宿主 `host_measure_flow_verify_ev` 79/79 已证明判定使用更新前前值） |
| 验收影响 | **影响** TD-002 INT-01 的“上电后立即有首条采样（`H=0`）”观测项：外部无法由 `S` 行复核判定所用的前一有效温度 |
| 责任 | **固件实现**：在推进前值前缓存 `prev/have` 供 `sensor_trace_fetch()` 使用（或由测试设计明确改变字段语义）；不得放宽判据 |

> 说明：这是**观测字段语义缺陷**，不是“采样/判定错误”。它使 INT-01 的观测判据不可满足，因此属于当前 `TEST_FAIL` 的一项真实软件原因；但它不能解释任何温湿度读数错误或上报错误。

## 4. 软件侧基线偏差 F-3：`delay_ms()` 实际约 1.626× 名义值

| 检查 | 结果 |
|---|---|
| 配置 | `GXHT40_MEASURE_WAIT_MS=20`（`sensor_config.h:60`） |
| 物理实测（两次独立） | 32.516 ms（本轮）/ 32.525 ms（EV-026）⇒ **1.626×** |
| 循环标定 | `main.c:96-106`：每 1 ms 参数执行 1592 次 `volatile` 内层递减；由 32.516 ms/31840 次 ≈ **1.021 µs/次**（两轮一致） |
| 调用点性质 | `gxht40.c:99` tMEAS、`gxht40.c:110` 读重试、`gxht40.c:185` tPU、`light.c:115/166`、`measure.c:196/203/234/363` 全部为**下限等待**；更长方向安全 |
| 数据手册余量 | 20 ms 配置 → 32.5 ms 实测仍远大于 GXHT40 `tMEAS.H max 8.3 ms`、`tPU max 1 ms` |
| 观测影响 | 未观察到任何 `q=0`/CRC/读数异常可归因于它；属基线不一致与潜在功耗/时序偏差 |
| 责任 | **固件实现**：若“`delay_ms` 名义毫秒”是产品要求，应重新标定并实板复核；若仅要求“不短于手册”，应在实现/设计文档中明确该语义。本轮不据此判功能失败 |

补充：`COMMON/delay.c:45` 的 `delay_us()` 本身已使用 `volatile`，E1 未改动它；UM2005C HAL 使用 10/50 µs（`um2005C.c:63/69/106/113`、`um2005C_hal.c:192`）。按同一递减结构推算约 1.02 µs/次，量级内；**本轮未做位级直接测量，不能作为通过证据**（本轮无发送周期）。

- 已被 20 ms A/B 削弱（等待余量已远超手册）；若器件内部状态机与命令后的等待时间无关，则更长等待也不会改变内容。

### H2′（主机读时钟速率兼容性）

- 未测试：rev 6.1 只改变了**采样相位**，未改变 **SCL 频率**（约 6–8 kHz）。若器件对时钟速率敏感（内部加载/输出时序），降速可能改变结果。
- 现有反证：同一主机代码对 6 个字节同构，无法解释“恰好第 3 字节整字节等于第 1 字节”。

### H3 总线电气（竞争/上升沿/接触不良）

- 反证：随机电气错误应同时出现湿度字节/CRC 错误与多位错；实测 24/24 只错第 3 字节。**可能性低**，但无位级/电气测量，不能硬排除。

### H4 MCU 内存/编译器缺陷（`buf[0]` 被复制到 `buf[2]`）

- 反证：源码无此类路径；同一缓冲第 4–6 字节正确；同一构建的宿主机 harness 与原语自检通过。**低概率保留**；仅在完全没有位级波形时，才需要专门的构建级对照。

### H5 器件型号/真伪/装配状态

- 支持：EV-017 时器件对任何地址（含 `0x00`）不应答，EV-018 起 `ack=44` ⇒ 两次运行之间板卡器件侧发生物理变化（重焊/换件/重新上电）；随后出现本签名。
- 反证缺口：无目视、无万用表、无换件条件。**未决**。

## 6. 软件侧故障边界结论

1. **已证实的软件事实**：`i2c_read_bytes()` 对 6 个字节执行同一循环、无索引分支；采样点、ACK/NACK、CRC 判定、失败语义、诊断快照均按实现工作；失败判定与 `G raw` 打印使用同一缓冲区。
2. **两项针对主机侧时序的 A/B 均无效**：采样相位后移（H2 子假设）与转换等待 10→20 ms（H1 等待子假设）都没有改变失败率与签名。⇒ 主机侧的这两个时序维度**不是**本失败的原因。
3. **不能由现有固件代码单独解释**：24/24 的“第 3 字节 = 温度 MSB”要求总线上该时隙真实呈现温度 MSB，或存在尚未发现的索引相关缺陷。本能力在源码中**未找到**后者。
4. **因此失败边界位于“器件输出第 3 字节 / 主机读取该字节时隙”的交界**。在取得位级 SDA 波形、或完成“读时钟速率”等未测维度的对照构建前，**不能把责任单向判给固件或器件**；H1′（器件输出内容）、H2′（主机读时钟速率）与 H5（器件型号/装配）是当前剩余的最小可区分集合。
5. **不宣告**器件损坏、不宣告固件不可修复、不改产品源码；未知原因保留为未决，并给出可执行的最小实验。

### 2.1 该签名不是 CRC 约定/帧布局差异

## 3. 定量特征（18 个已观测周期）

| 统计 | 数值 |
|---|---|
| 观测周期 | EV-018 的 15 个（run1 8 + run2 7）+ 本轮 3 个 = **18** |
| `q=1` | 11 |
| `q=0` | **7（38.9%）** |
| 失败周期行 | 全部 `s=4 a44=1 a45=0 rd=0 at=3` |
| 8 个失败帧中湿度 CRC 错 | **0** |
| 8 个失败帧中 `raw[2]==raw[0]` | **8** |

- `a44=1 / a45=0 / rd=0`：器件在 0x44 应答、读事务第一次即完成（无读地址 NACK 重读）、失败的 3 次测量重测全部发生在 **CRC 校验层**。
- `at=3`：失败周期内 3 次“重新发 0xFD + 重读”全部 CRC 失败。
- 若把 3 次读事务视为相互独立，单次读通过率 `p` 满足 `1-(1-p)^3 = 11/18` ⇒ `p≈0.27`（≈73% 的单次读出现该错）。**这是条件推断**；若同周期内存在相关性，则单次失败率会更低。两种情形都无法由现有串口数据区分。
- 失败帧的数据字换算后为 **22.7–25.9 ℃ / 35.0–40.0 %RH**，与同窗口成功周期一致 ⇒ **数据字本身正常**，不是采集通道整体失效。
- 失败在不同 `k`、不同温度/湿度值上随机分布（k=0/3/6/12/15/30/39），与时间、温湿度数值、相邻周期成败均无可见相关。

## 5. 竞争假设（保留，未决）

### H1（优先）器件侧“温度 CRC 字节加载/输出竞争”

器件在把温度 CRC 装入输出通路之前就被主机器读出，移出的是仍留在输出寄存器中的温度 MSB。

- 支持：8/8 精确等于 T_MSB；错误严格限定在第 3 字节；第 6 字节（湿度 CRC，距读取起点最远、可用加载时间最长）8/8 正确；间歇且与数据值无关。
- 反证缺口：需要**位级 SDA 波形**才能确认线上第 3 字节确实是 T_MSB（而不是主机读回错）。

### H2 主机读时序与器件不兼容（固件侧）

`sf_i2c.c: i2c_read_byte()` 在释放 SCL 后**立即**采样 SDA（写路径 `i2c_write_byte()` 在 SCL 高后有整段 `i2c_delay`，读路径没有）；总线约 6–8 kHz（`speed=100`）。

- 支持：读路径与写路径的采样点不对称，属可改进项。
- 反证：该函数对 6 个字节**完全同构**，无按索引分支；单纯采样过早应产生随机位错，无法解释“第 3 字节恰好整字节等于第 1 字节”。
- 状态：**未排除**，但现有源码中找不到能产生该签名的索引相关路径；需对照构建或位级波形。

### H3 总线电气（竞争/上升沿/接触不良）

- 反证：若为随机电气错误，应同时出现湿度字节/CRC 错误与多位错；实测 8/8 只错第 3 字节且值为 T_MSB。**可能性低**，但未做位级测量，不能硬排除。

### H4 MCU 内存/编译器缺陷（`buf[0]` 被复制到 `buf[2]`）

- 反证：源码无 `buf[2]=buf[0]` 类路径；同一缓冲区第 4–6 字节正确；无证据。**低概率保留**。

### H5 器件型号/真伪或重焊状态

- 支持：EV-017 时器件对任何地址（含 `0x00`）不应答，EV-018 起 `ack=44` ⇒ 两次运行之间板卡器件侧发生了物理变化（重焊/换件/重新上电）；随后出现本签名。
- 反证缺口：无目视、无万用表、无换件条件。**未决**。

## 6. 软件侧故障边界结论

1. **已证实的软件事实**：读原语 `i2c_read_bytes()` 对 6 个字节执行同一循环、无索引分支；CRC 判定、失败语义、重试上限、诊断快照均按实现工作；失败判定与诊断打印使用同一缓冲区。
2. **不能由现有固件代码单独解释**：8/8 的“第 3 字节 = 第 1 字节”要求总线上该时隙真实呈现温度 MSB，或存在尚未发现的索引相关缺陷。本能力在源码中**未找到**后者，也未发现任何“选择性复制第 1 字节到第 3 字节”的路径。
3. **因此失败边界位于“器件输出第 3 字节 / 主机读取该字节时隙”的交界**。在取得位级 SDA 波形或完成对照构建前，**不能把责任单向判给固件或器件**；H1（器件输出/加载竞争）与 H2（主机读时序兼容性）是当前最小可区分的一对。
4. **不宣告**器件损坏、不宣告固件不可修复、不改产品源码；按要求把未知原因保留为未决并给出可执行的最小实验。

## 10. 归因结论

- **失败可复现且签名高度稳定**：GXHT40 读回的 6 字节中，**仅温度 CRC 字节**间歇性错误，且 8/8 精确等于温度 MSB；湿度数据与 CRC 始终正确；失败发生在 CRC 校验层（`s=4`），地址已应答、读事务已完成。
- **该签名不能由协议/CRC/布局约定解释，也不由本交付 T1–T3 引入**（旧镜像同签名）。
- **软件侧边界**：读原语与判定路径无索引相关分支，未发现可产生该签名的固件机制；但仅凭串口数据无法排除主机读时序（H2）。
- **未决主因**：器件第 3 字节输出/加载竞争（H1）与主机读时序兼容性（H2）需位级波形或对照构建区分；器件型号/重焊状态（H5）需硬件核对。
- 结论类型：`FAILURE_ANALYZED`（有效归因产物完成，**不等于产品修复或测试通过**）。
