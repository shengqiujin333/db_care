```text

                                                                                                 '--HTTP(:5000)------->  [/upload_data]
```

| 部件 | 作用 | 本轮状态 |
|---|---|---|
| 传感器 | 每 3 分钟采样温度/湿度与光照，按条件判定是否经 433 上报 | **已修改**（FD-002 rev 8，已发布候选包） |

| iOS App | 不属本次修改范围 | 未修改 |
| 平台服务 | EMQX broker + Flask HTTP（`/upload_data` 等 6 个 POST 路由）+ MySQL | 既有部署，只读核验，未变更 |

## 3. 上报判定规则（精确语义）

固件判定函数 `sensor_decide_report(cur, prev, have_prev, dark)`：

```text
若 cur > 350                       → 上报（cur/prev/dark 单位 0.1 ℃/0.1 %RH）
否则若 have_prev && dark
        且 (cur - prev) > 9        → 上报
否则                               → 不上报
```

| 边界 | 行为 |
|---|---|
| 本次比上次高 0.9 ℃（差值 = 9） | **不上报**（严格大于） |
| 本次比上次高 1.0 ℃ 及以上，且 `dark=1` | 上报 |
| 温度恰好 35.0 ℃（350） | 超温分支**不**满足；若满足升温且无光分支仍可上报 |
| 温度 35.1 ℃ 及以上 | 上报（与是否有光无关） |
| 无前一有效样本（上电首周期） | 升温分支不成立；>35.0 ℃ 仍可上报 |
| 采样失败（`q=0`） | 不上报、不推进前值、不构造 0 值、不覆盖冻结快照 |

**"无光"的当前状态（关键限制）**

- 判据形制为 LIGHT-DEF-2：`dark = valid && (mean_adc >= LIGHT_DARK_THRESHOLD_CODE)`，整数比较、边界相等算暗、无滞回、无跨周期状态。
- 交付固件 `LIGHT_DARK_THRESHOLD_CODE = 0`（唯一禁用值）⇒ `valid=false`、`dark=false`，**升温+无光分支在交付固件中不会触发**；只有严格 >35.0 ℃ 分支可用。
- 这是设计 §6.2 的安全默认，不是缺陷；在没有"判据数值接受记录 + 同板同构建双态被动证据"前不得回填阈值。实板观测（EV-036，6 个周期）全部 `V=0 D=0`，与默认一致。
- 因此**当前交付不满足需求 4 的完整语义**，验收与交付必须明示这一点。

## 4. 数据与时间语义（影响使用与判读）

1. 传感器每 3 分钟采样一次，但**只在满足上报条件时才经 433 发送**；App 看到的记录是"上报时刻"，不是连续采样序列。
2. App 的 `time` 字段是 **BLE/MQTT 接收秒**，不是传感器物理采样时刻；卡片不得据此推断设备离线（1.9 已移除"离线"语义）。
3. 网关会缓存最近记录，App 每 180 s 读取一次；同一数值可能以不同接收时间重复出现（网关缓存复读），不构成链路故障。
4. 光照数据**不上传**：不进 433 报文、不进 App 上报请求、服务端无光照列。
5. 上报 ≠ 报警：App 的下降/超限/紧急报警是 App 侧独立判定。
